# 正式交付规范

本规范记录所有者在“v5.1.10 正式合并发布及后续开发交付规则调整”中的明确持续授权；不伪造签名或确认时间。
仅适用于 inkzcz/life-journal_public 的正常版本，新的明确限制优先。v5.1.9 的历史授权、Tag 和附件保持不变。

1. 在独立分支完成需求、测试、来源/秘密/第三方审核和文档，创建 PR。Draft 只用于未完成工作；门禁满足后转 Ready。
2. 为具体版本增加独立 binary authorization，记录来源 PR、已审核功能基线、公开单业务 TAR/源码范围与授权依据，保持 Registry、NAS 和原私有仓库操作为 false。必要时安全扩展版本选择器并加负向测试，不能开放任意版本。
3. 对发布工作流做技术审核，登记精确 SHA256；它是执行者审核记录，不是所有者逐字节签名。只读源码/构建作业不持有发布写令牌。必要检查必须对应最终 HEAD，PR 与分支 CI 通过后普通 merge，main CI 也通过。
4. 只在已验证的 main 普通合并提交创建新 Annotated Tag。远端 tag 对象必须直接指向授权 PR 合并提交；冲突即停，不删除、移动或覆盖。应用与调度源码分别绑定，禁止用其他工作树冒充 Tag。
5. Actions 对正式 Tag 构建一次 linux/amd64 Debian 统一业务镜像，API/Web/Maintenance 三个角色复用。单 TAR 不含独立数据库镜像。CI 可独立准备 PostgreSQL17 测试设施；本地交付工具不处理数据库镜像。
6. 正式构建执行完整 PG17/SQLite、前端/类型/构建、Windows 启动器自动化、浏览器合成验收、来源与版本、全层密钥扫描、重复 load、四容器/登录/重启/持久化、备份/独立恢复及适用升级回归。不得把旧提交绿色状态当成本次验证。
7. 每次实际镜像按依赖真实身份生成精确对应源码、补丁、版权/NOTICE、构建材料及 Psycopg/Pillow 修改替换/重链接收据。法律包逐文件哈希并绑定本次业务 TAR、config、版本和源码提交；缺少具体组件义务就停止上传。
8. 只允许10个契约附件：唯一业务 TAR、对应源码/许可证归档、部署 ZIP、manifest.json、images.json、SHA256SUMS.txt、INSTALL.md、UPGRADE.md、KNOWN_LIMITATIONS.md、RELEASE_NOTES.md。禁止上传数据库/媒体/备份/原始敏感日志。
9. 先创建草稿 Release 并上传完整附件；重新下载全部字节、核对 SHA256SUMS 本体及各附件、单镜像/架构/标签/来源，再转正式非预发行 Release。不能把测试候选、仅源码 ZIP 或本地成功称为完成。
10. 报告合并/Tag/源码 SHA、CI/Release/TAR 下载链接、大小/SHA256、数据库兼容、升级回滚步骤和未执行事项。正常通过后继续至正式可部署交付，不重复询问许可。

Windows Docker Desktop、极空间 Z4S、真实用户数据库和真实 WxPusher 终端投递由所有者发布后本地验收。Linux 自动化、合成数据或旧版本实机记录不替代它们。UPGRADE-001 历史根因未确认，不宣称修复，不绕过任何迁移保护。

出现实际失败、安全/数据丢失风险、必要许可证缺口、权限/计费/分支保护或明确仅开发指令时暂停受影响发布，先安全修复可修复事项。不得连接 NAS、操作生产库/媒体、删除旧镜像或覆盖历史发行。生产部署和用户验收由用户执行。
