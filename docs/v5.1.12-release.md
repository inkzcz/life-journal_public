## 发行契约

继续只交付一个 Debian Linux/amd64 业务镜像 `life-journal:v5.1.12`，API/Web/Maintenance 复用，PostgreSQL17 独立部署。不推送 Registry，不访问 NAS，不打包数据库镜像或私人数据。十项正式附件为唯一业务 TAR、精确对应源码/许可证归档、部署 ZIP、manifest/images、SHA256SUMS、安装、升级、已知限制及发行说明。

原始版本级授权登记保留在 `licensing/BINARY_RELEASE_v5.1.12_AUTHORIZATION.json`；正常来源补充登记为 `licensing/BINARY_RELEASE_v5.1.12_SOURCE_BINDING_AUTHORIZATION.json`，绑定最终修复 PR11 的普通合并及精确 HEAD/main CI，原PR10登记字节与SHA不变。补充登记不代表新的人工审批，不授权改写Tag。原始登记根据当前用户完整任务第15/16/19节及既有持续交付规则登记，绑定实际 PR10。它是执行者登记，不是电子签名，不包含伪造时间，也不授予历史 Tag 改写权限。v5.1.11 已正式发行，Tag、授权、附件及410份历史法律文本保持不变。

必须先完成精确 PR HEAD 的必要门禁，普通合并后验证 main，才创建指向最终PR11普通合并提交的新 annotated Tag；正式工作流还验证远端 Tag 对象、PR 第二父提交、main CI、工作流 SHA 和来源身份。源码/构建作业不持有发布写令牌。草稿附件回下载及匿名公开字节校验继续保留，只有成功后才清理该次精确中间 artifact。测试截图保留7天，正式构建中间 artifact 保留1天；正式 Release 资产不清理。

## v5.1.11 → v5.1.12 升级

本版沿用 `0021_anniversary_calendar`，新增阅读/AI配置存放于现有可扩展配置，引用治理复用现有索引；不新增 Alembic revision，不重写历史迁移。仍需核查数据库版本，不能通过删除库、`stamp` 或关闭约束升级。没有新增强制环境变量、Compose 部署方式或模型重新配置要求。新增服务商密钥如有使用，仍以自行配置的 `LJ_AI_KEY_*` 引用提供。

1. 使用原 v5.1.11 构建停止外部写入，私下备份 `.env`、Compose/override、项目名、目录映射及旧镜像身份。用旧 Maintenance 创建并验证完整备份，并在独立项目与新空 DB/媒体目录完成恢复演练。不要覆盖已有备份。

   ```sh
   docker compose --env-file .env exec --user 10001:10001 -T maintenance python -m app.backup create
   docker compose --env-file .env exec --user 10001:10001 -T maintenance python -m app.backup verify --id BACKUP_UUID
   ```

2. 仅在正式发行后下载完整 v5.1.12 附件，核对 `SHA256SUMS.txt` 及来源身份。导入唯一业务 TAR，核对 `linux/amd64`；保留旧业务镜像和原 PostgreSQL17，不重新标记旧镜像。

   ```sh
   docker load -i life-journal-app-v5.1.12-amd64.tar
   docker image inspect life-journal:v5.1.12 --format '{{.Os}}/{{.Architecture}}'
   ```

3. 保持原项目与全部 DB/MEDIA/BACKUP 路径，只把私密配置 `IMAGE_TAG` 改为 `v5.1.12`。已有 `-p`/多个 `-f` 参数继续原样使用，不用新 ZIP 覆盖原私密配置。

   ```sh
   docker compose --env-file .env config --quiet
   docker compose --env-file .env stop web api maintenance
   docker compose --env-file .env up -d --pull never
   docker compose --env-file .env ps
   ```

4. 只读检查 `SELECT version_num FROM alembic_version;` 仍为 `0021_anniversary_calendar`。若旧库不是该受支持基线，先依主升级文档执行已有显式迁移流程，不清空数据、不强行启动 API。本次同 Schema 升级不需要新增迁移命令；原 `app.migrate` 和 Maintenance 保护保持生效。
5. 核对 `/api/health`、登录、管理员 `/api/blog/build-info` 的版本与正式来源提交；检查历史文章/修订/UUID、六类卡片、交通时区、旧 @ 标记、图片、地点、行程、回收站、引用分类、AI默认模型和自定义颜色，创建并验证新版备份。无需为读取历史文章而手动重建所有索引；维护页面的一致性检查与重建应先预览再显式确认。

真实生产操作由部署者执行；本任务的自动化不连接真实 NAS 或真实数据库。

## 合成升级基线与回滚

容器升级演练只接受正式 v5.1.11 业务 TAR SHA256 `fcf1971553ba1cc4ef9056ac41b73d907a22772446031e3ce1aed93f4677fae0`、正式来源 `5747934d1304ac87ab60489c8d7a46ec99e58593`、Linux/amd64 和唯一业务镜像标签。演练使用新隔离目录，包含旧文章、动态字段、六类卡片、媒体、行程、模板与通知，并新增旧 AI 模型UUID、端点、启用状态、默认模型和密钥引用的逐项保留验证。是否通过必须查阅本版实际收据；单元测试不等于容器演练已通过。

升级后写入的新字段、新 AI `services`/`task_defaults` 配置不保证旧程序理解。同 Schema 也不代表任意安全降级：停止业务写入并保留升级后数据，不执行破坏性 downgrade、不删除目录、不覆盖原库。状态不明或已有写入时，用升级前完整备份、精确旧构建及 PostgreSQL17在独立新目标恢复验证后，再由部署者决定切换。旧备份不包含升级后的新增内容，须另行保全。详细恢复步骤遵从 `docs/backup-restore.md`。
